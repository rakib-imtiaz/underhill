Real-city flight · 4 scenarios · 8 tests each

Which real city should the drone fly over?

The same drone (our M350 model), the same controls and the same scripted 20-second flight, over the same real place: Metrotown, Burnaby, between Hyatt Place and MetroPlace (49.2249° N, 123.0034° W), about 4 km west of Underhill's Burnaby office. Each scenario page runs the same eight tests and shows what passed, what failed and the measured numbers.

Recommendation

Build the real-city mode on A: three.js + OpenStreetMap. Keep B: Google 3D Tiles as an optional “photo-real” switch, once you have tested it with your own key and accept per-visit billing.

  • A is free and ours. No key, no account, no per-visit cost, and it works offline. It is the same engine as fly mode, so the drone, collision, LiDAR and night lighting carry over unchanged. It is the only scenario that passed all 8 tests: first frame in 2.1 s, 1.8 MB to download, and a median frame of 10.9 ms (p95 15.3 ms) on the scripted flight.
  • A looks like a clean architectural model, not a photo. It has real footprints and heights, window grids, lit windows at night, roads, the SkyTrain guideway and trees. For a survey company that is on-brand: it is honest and it reads as a map. The cost is that it never looks like the actual street.
  • B is the only option that looks like the real place. It needs your Google key and billing, and every visitor's view streams from Google. Daylight is baked into the photos, so there is no real night, and the mesh has no building or ground labels. It is untested here until you paste a key.
  • C and D did not earn the switch. C (MapLibre) is free, but it stuttered while tiles streamed (p95 147 ms). Its camera cannot look at the horizon, and it has no 3D raycast of its own. D (Cesium) is a capable GIS globe, but its free tier is non-commercial. It adds a second engine of about 2.8 MB, ran slowest per frame (median 55 ms on fallback data), and its picking costs about 11 ms per ray.

What each test does

Load time to first frame
Time from opening the page to the first drawn frame. For map engines there is a second number: when the first real map content (tiles) is on screen. Pass ≤ 3 s, partial ≤ 6 s.
Frame time, scripted 20 s flight
“Run tests” flies the same route everywhere: take off, fly between Hyatt Place and MetroPlace at 35 m, a climbing half orbit of Hyatt Place, then land (291 m, up to 20 m/s). 1,200 frames at a fixed 1/60 s step. Each frame waits for the GPU, and we report the median and the 95th percentile. Pass: p95 ≤ 16.7 ms (60 fps). Partial: p95 ≤ 33 ms.
Download size
Compressed bytes for the visit, including tiles streamed during the route. Pass ≤ 8 MB, partial ≤ 25 MB.
Building collision
Full forward stick at Hyatt Place from about 62 m out, 40 m up. It passes if the drone brakes and stops short of the wall without entering the footprint.
LiDAR raycast
From a hover in the gap, the lab casts 96 rays: 64 level and 32 sloping down. It counts building hits, times each ray, and checks the distances against the OpenStreetMap footprints.
Day / night
What the engine can do for night. The lab also measures the mean frame brightness from one viewpoint, day then night.
Phone viewport (390 px)
A 390 × 844 copy of the page checks for sideways scroll, a full-width 3D view, a folded panel, touch sticks and the attribution on screen. Touch feel still needs a real phone.
Attribution
The legally required credit (OpenStreetMap, Google, Cesium) is on screen, not covered, and has the right words.

How to read the numbers

  • Hidden tab. The lab's own run happened in a background browser tab. Background tabs do not run the normal animation clock, so a worker clock drove the frames. Results marked hidden tab should be confirmed in a visible tab: open a scenario, press Run tests, and come back here.
  • Same machine for all four: an AMD Radeon integrated GPU, a 1,638 × 1,135 px window at 1.1× pixel ratio. Other work shared the machine during the runs, so frame times vary by roughly ±30 % from run to run (D measured 39 ms and later 55 ms). The ranking matters more than the absolute numbers.
  • Sizes come from the local dev server, which does not compress. A production server would send the 0.94 MB OpenStreetMap file at roughly 0.2 MB.
  • Keys stay in your browser. B and D keep your key or token in localStorage on this machine. Nothing is written to the files.

Out of scope

  • Mapbox GL JS. Since v2 it is not open source. It needs a Mapbox token and is billed per map load after the free allowance. MapLibre (C) is its open fork and covers the same ground.
  • WebODM. This is a photogrammetry pipeline, not a map source. It turns our own drone photos into a 3D model of one site. It fits later, for real Underhill job sites, but there are no Metrotown photos to feed it.
